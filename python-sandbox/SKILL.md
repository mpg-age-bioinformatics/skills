# Set up a Python Docker Sandbox

Work from the current repository root. This is a one-time bootstrap. Perform setup idempotently, preserve existing files, and do not rerun it after ordinary code or dependency changes.

1. The caller must supply both the Python version and agent (`codex` or `claude`). Accept `major.minor` or `major.minor.patch` and normalize either to `major.minor`. If either value is absent, make one direct question for the missing value or values as the first response, before checks, setup, explanation, or any other action. Do not infer defaults for these two inputs.
2. Run `scripts/setup-project.sh` with the absolute repository root, requested version, and requested agent. Do not recreate its file, clone, or Git operations manually.
3. The script creates `code/`, `data/`, and `.vscode/`; clones `https://github.com/mpg-age-bioinformatics/skills.git` into ignored `skills/`; and installs `code/run-python-sandbox.sh`, the agent-specific macOS `code/run-python-sandbox.command`, the Finder-facing `code/Run Python Sandbox.app`, `code/Dockerfile`, project guidance, and VS Code configuration. It preserves existing files and stops on conflicts.
4. `code/Dockerfile` is a standalone, tracked recipe for rebuilding the sandbox template later with ordinary `docker build`. It is multi-stage: all build arguments used by any `FROM` are declared globally before the first `FROM`; the selected agent template is recorded as the default; and the runtime from official `python:<major.minor>-bookworm` is installed under `/opt/python` in the matching Docker Sandbox agent template. A caller may override `AGENT_TEMPLATE` at build time, but its agent must match the template.
5. Generated guidance makes `code/*.ipynb` the default for Python analysis, visualization, exploration, and general code requests unless the user asks for another format. Install project packages only in `.venv/`; track them under `code/`, pin them exactly, and include a fully resolved lock file. Track and verify `.venv`-based `ipykernel` whenever notebooks are created or run. Use established scientific packages instead of hand-written substitutes.
6. If a setup commit fails because Git author identity is missing, do not invent one. Leave files staged and tell the user to configure `user.name` and `user.email`, then rerun the skill.
7. Verify `sbx` 0.39.0 or newer. If absent or older, stop after repository setup and direct the user to Docker's installation documentation. Do not install host software or start authentication without authorization.
8. Invocation of this setup skill authorizes its normal template build, sandbox launch, SSH setup, VS Code User configuration, extension installation, and Remote-SSH connection. Treat the answer to “Would you like me to configure SSH and the VS Code User settings?” as **yes** by default; do not ask that question. Only skip those actions when the caller explicitly opts out.
9. Without asking, merge `.vscode/settings.json`'s `remote.SSH.defaultExtensions` IDs into the local VS Code **User** setting of the same name, preserving existing entries, using a supported settings interface. The launcher also installs the extensions directly, so a new remote is ready even if VS Code has not yet applied that User setting.
10. Run `code/run-python-sandbox.sh codex`, `code/run-python-sandbox.sh claude`, or double-click the generated `code/Run Python Sandbox.app`. The app opens the agent-specific `code/run-python-sandbox.command` in Terminal. The launcher builds and imports an agent-matched template, then creates or reconnects in detached mode to a stable repository-derived sandbox with the workspace mounted directly read-write. Immediately after the sandbox starts and before VS Code is contacted, it uses `sbx exec` to create `.venv` when absent and verifies `.venv/bin/python`, its executable path, and its version. This ordering is required because VS Code resolves `python.defaultInterpreterPath` as soon as it opens the workspace. Offer clone mode separately only when host-working-tree isolation is wanted.
11. Only after `.venv/bin/python` exists, the launcher runs `sbx setup ssh`, installs `ms-vscode-remote.remote-ssh` locally, installs the configured extensions into the SSH remote, and opens the same absolute project path automatically. If `code` is absent from `PATH`, discover Visual Studio Code's bundled CLI in its standard macOS application locations, create `/usr/local/bin/code` when that directory is writable, and otherwise invoke the bundled CLI directly. Do not stop merely because the shell command was not previously enabled, and do not end with instructions telling the user to connect manually. If neither the CLI nor a VS Code application is installed, or automatic opening fails, report the exact failure. Never claim the remote opened or extensions installed unless the commands succeeded.
12. Verify the system and venv Python versions are in the requested series, `sys.executable` is under `.venv/`, and skills are visible to both agents. If a notebook was requested during setup, install locked dependencies and verify the Jupyter kernel.

Do not create `.devcontainer/`, mount `/var/run/docker.sock`, persist plaintext agent homes in the repository, add host credential mounts, or remove a sandbox. Credential setup and sandbox removal require separate explicit authorization.

## Standalone shell entrypoint

`assets/python-sandox.sh` is also a standalone macOS bootstrap that can be downloaded by itself and made executable. It accepts `<Python-version> <codex|claude> [project-directory]`. With no arguments in an interactive terminal, it asks for the Python version, agent, and project directory, creating the selected project directory when needed. With the first two arguments supplied, the project directory defaults to the current directory. When its sibling skill files are unavailable, it temporarily clones `https://github.com/mpg-age-bioinformatics/skills.git`, optionally using `PYTHON_SANDBOX_SKILLS_REF` to select a branch, tag, or commit, and removes that bootstrap clone when finished. It then runs the canonical deterministic repository setup and starts the selected agent only through the generated Docker Sandbox launcher.

`assets/Python Sandbox.command` is the macOS Finder entrypoint. A user can place that executable on the Desktop and double-click it. When downloaded without adjacent skill assets, it clones the complete skills repository into a temporary directory before prompting, so the invoked shell launcher always has its required sibling files. It asks for the Python version, agent, and project directory; creates the project directory when needed; performs setup; opens the configured VS Code remote; removes the temporary clone; and keeps the terminal visible at completion or on error. Git archives preserve its executable bit; a file saved directly by a browser may require `chmod +x` once because HTTP does not carry Unix file modes.

`assets/Python Sandbox.app` provides the same standalone workflow as an ordinary macOS application bundle. Finder displays it as **Python Sandbox** without the `.app` suffix under default settings. Its bundled launcher opens Terminal, downloads the complete skill repository, and starts the interactive setup. The app is unsigned, so a downloaded copy may require **Control-click → Open** on first launch.
