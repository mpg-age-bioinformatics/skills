# Set up a bioinformatics Docker Sandbox

Work from the current repository root. This skill configures the repository; Docker Sandbox creation remains an explicit user-selected launch because each sandbox runs one chosen agent.

1. Obtain the selected agent (`codex` or `claude`), asking only when the caller has not selected one, then run `scripts/setup-project.sh` with the absolute repository root and that agent. Do not recreate its copying, cloning, or Git operations manually.
2. The script creates `code/`, `data/`, and `.vscode/`, clones `https://github.com/mpg-age-bioinformatics/skills.git` into ignored `skills/`, installs the launcher at `code/run-bioinformatics-sandbox.sh` and the agent-specific `code/Run Bioinformatics Sandbox.exe`, and adds root `AGENTS.md`, `.instructions.md`, extension recommendations, workspace settings, and LF-only Git attributes for shell launchers. It preserves existing files and stops on conflicts. When `BIOINFORMATICS_SANDBOX_SKILLS_REF` is set, the project-local skills clone uses that exact revision.
3. The generated policy keeps scientific code, Dockerfiles, and dependency manifests under `code/`, data and outputs under `data/`, and requires appropriate scientific libraries. It explicitly requires CSV-backed heatmaps to use Pandas with Seaborn/Matplotlib and a direct `sns.heatmap(...)` call by default; missing packages must be added as pinned dependencies rather than replaced with manual CSV parsing, SVG/XML construction, color interpolation, or custom heatmap rendering. Workload containers are built and run only when dependencies or isolation require them. They run on the Docker daemon private to the Docker Sandbox, never through a host Docker socket or a VS Code Dev Container.
4. If the setup commit fails because Git author identity is missing, do not invent or configure one. Leave files staged and ask the user to configure `user.name` and `user.email`, then rerun the skill.
5. Verify the host has `sbx` 0.39.0 or newer with `sbx version`. If it is absent or older, stop after repository setup and direct the user to Docker's installation documentation. Do not install host software or start authentication flows without explicit permission.
6. Invocation authorizes the normal sandbox launch, SSH setup, VS Code configuration, extension installation, and Remote-SSH connection; do not ask separately whether to perform them. Run `code/run-bioinformatics-sandbox.sh codex`, `code/run-bioinformatics-sandbox.sh claude`, or double-click the generated `code/Run Bioinformatics Sandbox.exe` on Windows. The launcher verifies `sbx`, then creates or reconnects to a stable path-derived sandbox in detached mode with the current workspace mounted directly read-write. On Windows, only local-drive workspaces are supported, and native host paths remain separate from the `/c/...` paths used inside the sandbox and by VS Code Remote-SSH. Explain that direct mode exposes the repository but not the rest of the host; offer clone mode separately only when requested.
7. Merge the IDs from `.vscode/settings.json` under `remote.SSH.defaultExtensions` into the local VS Code **User** setting of the same name, preserving existing entries. The launcher also installs these extensions directly into the remote so a new connection is ready immediately.
8. The launcher runs `sbx setup ssh`, installs `ms-vscode-remote.remote-ssh` locally, installs the configured extensions under `SSH: <sandbox-name>.sbx`, and opens the same absolute project path automatically with VS Code Remote-SSH. If `code` is absent from `PATH`, it discovers Visual Studio Code's bundled CLI in standard macOS application locations, enables `/usr/local/bin/code` when writable, and otherwise invokes the bundled CLI directly. Do not finish with manual connection instructions unless automatic opening actually fails, and never claim VS Code connected or extensions installed unless the commands succeeded. Only skip this default behavior when the caller explicitly opts out.
9. Explain that Docker Sandboxes use a microVM boundary with a private filesystem, network, and Docker daemon. The built-in `-docker` agent templates may run workload containers with privilege inside that microVM, but they do not expose the host Docker daemon. Sandbox-installed packages, images, containers, and remotely installed VS Code extensions persist across sandbox stops and are discarded when the sandbox is removed.

Do not create `.devcontainer/`, mount `/var/run/docker.sock`, persist plaintext agent homes in the repository, add host credential mounts, or remove a sandbox. Credential setup and sandbox removal require explicit user authorization.

## Standalone shell entrypoint

`assets/bioinformatics-sandox.sh` performs the same repository setup and launch without first running Codex or Claude on the host. It accepts `<codex|claude> [project-directory]`; when the agent is absent in an interactive terminal, it asks for it before doing any work. The project directory defaults to the current directory. It runs only the deterministic host-side setup before starting the selected agent inside Docker Sandbox, configuring SSH and extensions, and opening the repository automatically in a connected VS Code window.
