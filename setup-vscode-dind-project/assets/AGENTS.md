# Execution environment policy

Apply these rules to all work in this repository:

- Store all generated implementation files under `code/`. This includes source code, scripts, notebooks, Dockerfiles, Compose files, and dependency manifests such as `requirements.txt`, `pyproject.toml`, `environment.yml`, `package.json`, and R package or lock files. Do not place these generated project files at the repository root or under `data/`.
- Store every data artifact under the repository's `data/` directory or an appropriate subdirectory. This includes supplied input data, downloaded data, generated or simulated data, intermediate datasets, caches, processed data, analysis results, and final output data. Do not place data files at the repository root or under `code/`; use subdirectories such as `data/input/`, `data/intermediate/`, and `data/output/` when useful.
- Maintain a code-version identifier that is independent of Git. Whenever Codex changes any implementation under `code/`, generate one new random exact eight-character lowercase hexadecimal value, for example with the equivalent of Python's `secrets.token_hex(4)`, and update the identifier once for that coherent change set. Define it in the output-generating source code as a constant such as `CODE_VERSION = "a1b2c3d4"`, or in a shared source module under `code/` that every output-generating path imports. Do not generate a new value on each program run, derive it from Git, require a clean Git state, or accept it as a manually supplied runtime argument. Add the identifier as its own dot-separated segment immediately before the extension of every generated output filename, using `name.<code-version>.ext`, for example `summary.a1b2c3d4.csv`. When the format supports metadata, also embed the same code-version identifier; otherwise write a correspondingly named provenance sidecar such as `summary.a1b2c3d4.provenance.json` under `data/` containing the code-version identifier, generating command, parameters, and timestamp. Do not overwrite output produced by another code version.
- Use the appropriate scientific computing and visualization libraries for scientific work; do not replace them with the Python standard library merely to avoid installing dependencies. For example, a Python heatmap must use a scientific stack such as NumPy/Pandas with Matplotlib or Seaborn, rather than hand-written CSV parsing and image generation.
- Scientific Python code and visualization code must run inside Docker, even when the host happens to have the packages installed. Create a Dockerfile and pinned dependency manifest under `code/`, build the image, and run the code and its tests through the nested Docker daemon in the Dev Container.
- Code that needs only standard Linux utilities/libraries or the Python standard library and is not scientific analysis or visualization may run directly in the current development environment.
- If code requires any additional system package, language package, runtime, service, or other non-standard dependency, create its Dockerfile in the relevant project directory under `code/`. Build and run that code, including its tests and dependency installation, inside the resulting container.
- Run all R code inside a container, even when it uses only base R. Create a Dockerfile containing the required R runtime and packages, then use that image for execution and tests.
- Do not install project-specific dependencies globally on the host or Dev Container merely to bypass this policy.
- Keep Docker build contexts narrow. Copy only required files, pin dependency versions when practical, use a non-root runtime user when compatible, and avoid embedding credentials or secrets in images.
- Mount input data read-only when practical. Mount only the necessary `data/` paths and use writable mounts for the relevant generated, intermediate, or output-data subdirectories when the task needs to write data.
- Capture the stdout and stderr of every docker run in a log file with the hash matching the files being outputted. Store logs alongside output data, using a naming convention such as `name.<code-version>.log` or `name.<code-version>.run.log`.
- This is a bioinformatician environment. When possible, prefer Python over other languages. Otherwise, R and Bash are the second and third best choices respectively.
- Use scientific libraries as a bioinformatician would do. For Python, prefer libraries such as NumPy, SciPy, Pandas, Matplotlib, Seaborn, Biopython, Scikit-learn, and specialized bioinformatics tools. For R, use Bioconductor and CRAN packages suited to bioinformatic workflows.
